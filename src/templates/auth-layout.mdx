# AuthLayout

Login/auth pages: a centered card on the page surface — the logo above it,
title/description in the card header, the sign-in content as `children`, and
muted links below. The auth logic (OIDC redirect, submit, validation) stays
in the app.

**The standard case is single sign-on** (OIDC/Keycloak): `children` is a
single primary button that redirects to the identity provider — no local
fields.

<Canvas of={AuthLayoutStories.SSO} />

For local accounts (the fallback without SSO), `children` carries the fields
from the form primitives instead — here with the title as the page's `<h1>`
(`headingLevel={1}`), "Passwort vergessen?" below the fields and, below the
card, the language switch and the legal links:

## Slots & props

| Slot / prop | Type | Required | Content |
|---|---|---|---|
| `logo` | `ReactNode` | — | Brand block, centered above the card. |
| `title` | `ReactNode` | ✅ | Card heading (e.g. "Anmelden"). Without `headingLevel` it is **not** a heading, but styled text in `CardTitle`. |
| `headingLevel` | `1`–`6` | — | Set ⇒ `title` becomes a real heading of that level (via `CardTitle asChild`, typography unchanged). Left out ⇒ today's behavior, unchanged. |
| `description` | `ReactNode` | — | Muted line below the title. |
| `children` | `ReactNode` | ✅ | The sign-in content: SSO button (standard) or fields from `FormItem`/`Input`/`Button`. |
| `footer` | `ReactNode` | — | Centered, muted zone below the card ("Passwort vergessen?"). |
| `width` | `"default" \| "prose"` | — | Width of the centered column. `default` (the default) = 448px, `prose` = 672px. See "Width" below. |

## Width

By default the column is `max-w-md` (28rem / **448px**) — the width of a
sign-in form: a few short fields that a wider column would only pull apart.

For **long page texts in the card** — terms of use, accessibility statement,
privacy policy — that is too narrow. For those there is `width="prose"`:
`max-w-2xl` (42rem / **672px**).

<Canvas of={AuthLayoutStories.LegalPage} />

**Why a prop and not a `className`.** The width limit sits on the *inner*
column, but the caller's `className` flows into the *root element* — so the
width wasn't reachable from the call site at all. A legal page that adopted
this template silently shrank from 720px to 448px because of it. `width` is
the way there; a `className` passthrough to the inner column would be the
wrong one, because it reopens the class surface that `layout-only-classname`
is meant to close.

**Why `max-w-2xl` and not `max-w-3xl`.** Two reasons, each independent of the
other:

1. `max-w-2xl` is the step this system **already** named for a reading
   column — `Container size="reading"` *is* the same 672px. A wide
   `AuthLayout` column thus matches a `reading` container instead of
   introducing a second, competing reading width.
2. WCAG 1.4.8 (AAA) limits a line to 80 characters. After subtracting the
   card's `p-6` (48px on this axis), `2xl` gives a measure of 624px, while
   `3xl` gives 720px — so `3xl` is the step that breaks the limit.

Both widths are Tailwind steps, not arbitrary values: the system stays on its
own steps. There is deliberately no third step — it would need a purpose that
can't be named today.

## Responsive behavior

- Fills the viewport height (`min-h-dvh`) and centers the card vertically
  and horizontally.
- The column is as wide as `width` says (`max-w-md` or `max-w-2xl`); on
  narrow screens the token margins (`gutter`) keep the distance to the edge,
  and `w-full` lets both widths follow along below their maximum.

## Do's & don'ts

- ✅ SSO as the standard: one full-width primary `Button` ("Mit JLU-Account
  anmelden"); the OIDC/Keycloak redirect belongs in the app, not in the
  template.
- ✅ Build fallback fields with the form primitives (`FormItem` wires label,
  error and `aria-*` automatically); error states via `FormItem error=` (see
  story "WithFieldError").
- ✅ Render auth errors from the identity provider (rejected, session
  expired) as content above the button — e.g. text in `text-error`.
- ✅ Render long page texts with `width="prose"`, not with a `max-w-*` class
  at the call site — that applies to the root element and doesn't change the
  column width.
- ✅ Set `headingLevel={1}` when the sign-in page should get its heading from
  the template — and then pass plain text as `title`. Without the prop the
  page has **no** heading, and the `h1` stays the call site's business. Why
  the default stays like this: a consumer puts its own `<h1>` element into the
  slot precisely because it never got a heading there — an automatically
  generated one would nest one inside the other. Rule and defaults per
  template: COMPONENT_GUIDELINES.md → "Page headings: who owns them".
- ❌ Don't put your own `<h1>` element **into** the `title` slot when
  `headingLevel` is set — that nests two headings.
- ❌ Don't force a two-column hero layout in here — that would be a new
  template, not a `className` rework.
- ❌ No navigation/sidebar: auth pages stand outside the AppShell.
