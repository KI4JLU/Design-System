# FormLayout

Settings/data-entry pages: a narrow single column — `PageHeader`, the form
sections as `children`, and a separated action row at the bottom. The
template renders **no** `<form>` element: the app puts its own
`<form onSubmit=…>` around it, so submit buttons in `actions` work naturally.

<Canvas of={FormLayoutStories.Settings} />

## Slots & props

| Slot / prop | Type | Required | Content |
|---|---|---|---|
| `title` | `ReactNode` | ✅ | Page title — a real heading, level set by `headingLevel`. |
| `headingLevel` | `1`–`6` | — | Level of the title in the document outline. Default `1` (so `<h1>`) — unchanged for every existing call site. `2` or lower for a page whose `<h1>` is already carried by the frame (admin shell, CMS). The typography does **not** depend on the level. |
| `description` | `ReactNode` | — | Muted line below the title. |
| `children` | `ReactNode` | ✅ | Form sections — one `Card` with `FormItem`s per section. |
| `actions` | `ReactNode` | — | Footer actions (save/cancel as `Button`s). |

## Responsive behavior

- A narrow column (`Container size="reading"`), page margins via tokens.
- From `sm` up the action row is right-aligned side by side; on mobile it
  stacks in reverse (`flex-col-reverse`), so the primary action is on top.

## Do's & don'ts

- ✅ Build fields only with the form primitives — label, error and `aria`
  wiring is solved there.
- ✅ Group related fields per `Card`; spacing with `Stack`.
- ❌ No second `<h1>` on the page: the rule and the `headingLevel` it calls for are in `docs/COMPONENT_GUIDELINES.md` → "Page headings: who owns them".
- ❌ Don't expect a `<form>` in the template — your own `<form>` wraps the
  template, not the other way round.
- ❌ Don't pull validation logic into the template; it owns only the skeleton.
