# Theming

Three appearance axes, each an attribute on `<html>`, each written by exactly
one provider. The tokens in `tokens.css` read the attributes, so a component
needs **no theme logic** — style it with tokens and every combination works.
There is no longer a style switch (rounded / pill): every component has
exactly one shape, and the `--ui-radius-*` tokens are fixed values.

| Axis | Attribute on `<html>` | Values (choice) | Provider · hook | `localStorage` key (default) |
|---|---|---|---|---|
| Color scheme | `data-theme` | `light` · `dark` · `system` | `ThemeProvider` · `useTheme` | `theme` |
| Contrast | `data-contrast` | `normal` · `medium` · `more` · `system` | `AppearanceProvider` · `useContrast` | `ui-shape-contrast` |
| Accent color | `data-accent` | `standard` · `teal` · `violet` · `green` · `rose` · `amber` | `AppearanceProvider` · `useAccent` | `ui-shape-accent` |

"System" is resolved in JS; `<html>` always carries the resolved value:
`data-theme` is `light|dark`, `data-contrast` is `normal|medium|more`. Both
providers follow the OS live while "system" is selected.

The user changes all three in the settings window: **`AppearanceSettings`**
are the ready-made rows for that (see "Components/Overlays/SettingsDialog").
Check new screens in **both** color schemes; in Storybook, contrast and accent
can be switched live for every story from the toolbar.

## Color scheme (light / dark / system)

- The active theme sits on `<html data-theme="light|dark">`.
- The `ThemeProvider` resolves the user's choice (light / dark / system),
  persists it in `localStorage` ("theme") and, for "system", follows the OS
  live. Switch it with `AppearanceSettings` or `useTheme().setTheme(...)`.

## Contrast and accent color — the `AppearanceProvider`

One provider for the other two axes, mounted once near the root next to the
`ThemeProvider`.

```tsx
<ThemeProvider>
  <AppearanceProvider>
    <App />
  </AppearanceProvider>
</ThemeProvider>
```

- **Contrast** (`useContrast`): `normal` ("Standard") is the design as drawn:
  the work surface (`--color-canvas`) and the sidebars (`--color-sidebar`) in
  one white, focus shown through highlight surfaces, fine lines. `medium`
  ("Mittel") sets the work surface off slightly while the sidebars keep their
  color: light `--p-gray-25` instead of white, dark `--p-gray-975` instead of
  `--p-gray-950`. Only the navigation column of a settings window always has
  a second color (`surface`). `more` ("Hoch") does the same, strengthens lines
  and muted text (`outline-variant` → `outline`, `on-surface-variant` →
  `on-surface`) and forces a visible focus outline on **every** focusable
  element (3px `focus-ring`, `!important`, because components turn their own
  outline off). `system` follows `prefers-contrast: more` or a forced-colors
  theme of the OS (→ `more`, otherwise `normal`) — the accessible default
  wherever the device asks for it.
- **Accent color** (`useAccent`, `ACCENT_COLORS`): `standard` is JLU blue;
  every other family replaces the whole `primary` family in light **and**
  dark, and everything drawn in `primary` follows it. `AccentSwatch` shows the
  color in a picker (`--accent-swatch-<accent>`).
- **Shape:** the fixed radii `--ui-radius-row/card/box/control/tile` carry the
  one shape into the app's own CSS too. A container may set
  `--ui-radius-control` locally (that is how `AppShellLayout` draws its bar
  search as a pill).
- `defaultContrast` / `defaultAccent` apply while nothing is stored; contrast
  and accent are stored under `<storageKey>-contrast` / `<storageKey>-accent`
  (`storageKey`, default `ui-shape` — the name from the time of the style
  switch, kept so that stored values survive).
- Without an `AppearanceProvider` the hooks return their defaults (`system` /
  `standard`) and the setters do nothing.

The no-flash script below covers only `data-theme`. There is none for
contrast and accent: until the `AppearanceProvider` has mounted, the `:root`
defaults apply (standard contrast, JLU blue), so a different stored choice
appears only after that.

## ThemeProvider: uncontrolled vs. controlled

The `ThemeProvider` runs in two modes:

**Uncontrolled (default, unchanged).** Without a `theme` prop the provider
owns the state: it reads the choice from `localStorage` (key via
`storageKey`, default `"theme"`), persists every change there and writes
`data-theme` on `<html>`. Existing consumers (CampusAgents) need no changes.

```tsx
<ThemeProvider>{/* as before */}</ThemeProvider>
<ThemeProvider storageKey="campus-theme">{/* own storage key */}</ThemeProvider>
```

**Controlled.** With `theme` + `onThemeChange` the app owns the state: the
provider reads and writes **no** `localStorage`, holds no choice of its own,
and `setTheme` (for example from `AppearanceSettings`) only calls
`onThemeChange` — the app feeds the new value back in. The provider still
resolves it ("system" → light/dark) and writes it to `<html data-theme>`: it
stays the only writer of that attribute — the app must not set `data-theme`
itself as well.

```tsx
const [theme, setTheme] = useAppTheme(); // the app's own state (context, store, …)

<ThemeProvider theme={theme} onThemeChange={setTheme}>
  <App />
</ThemeProvider>
```

| Prop | Type | Default | Effect |
|---|---|---|---|
| `theme` | `"light" \| "dark" \| "system"` | — | Set = controlled mode: the provider follows this value and ignores `localStorage`. |
| `onThemeChange` | `(theme: Theme) => void` | — | Called on every `setTheme`; in controlled mode its only effect. |
| `storageKey` | `string` | `"theme"` | Uncontrolled only: the `localStorage` key. Must match the no-flash script. |

Not supported: switching between controlled and uncontrolled during the
provider's lifetime.

## Migration for apps with their own theme context (e.g. JustRAG)

An app whose own context already writes `data-theme` on `<html>` and uses the
same `localStorage` key must not simply mount both providers — that would be
two writers on the same attribute and key. Two ways:

**(a) The app keeps control — controlled mode.** The app context stays the
owner of the theme (and the language, if any); the DS provider gets `theme` +
`onThemeChange` and only resolves the value and writes the DOM. The app
context removes its own `data-theme` writes; persistence stays with the app
(its own key, its own format — for example only `light|dark`).

**(b) The app hands over control — uncontrolled DS provider.** The DS
provider owns the theme (including "system" and persistence, key selectable
via `storageKey`); the app moves i18n/language into a context of its own and
deletes its theme part.

**Recommendation (proposal, owner sign-off pending): way (b).** Reasoning: the
DS provider is the more complete implementation ("system" that follows the OS
live, the no-flash script contract, one documented storage contract), and way
(a) leaves two theme state machines in the project for good that have to be
kept in sync. Bundling theme and language in one context was a stopgap
anyway — separating them is a small one-off refactor, after which every
concern has exactly one owner. Way (a) remains the right one when an app
really manages the theme on the server or per user profile (then the app is
the legitimate owner).

## No-flash script

So the page doesn't flash light before React loads, this script belongs in
the `<head>` of `index.html` (identical to the ThemeProvider's logic — keep
both in sync). **Without this script the light theme flashes up in the dark
theme** until the provider mounts — JustRAG's `web/index.html`, for example,
doesn't have it today. With a different `storageKey` (or controlled mode with
its own persistence), adapt the script accordingly — it must read the same
key and the same values as the actual theme owner:

```html
<script>
  (function () {
    try {
      var t = localStorage.getItem("theme") || "system";
      var dark =
        t === "dark" ||
        (t === "system" &&
          window.matchMedia("(prefers-color-scheme: dark)").matches);
      document.documentElement.dataset.theme = dark ? "dark" : "light";
    } catch (e) {
      document.documentElement.dataset.theme = "light";
    }
  })();
</script>
```

## Requirements for every theme

Every theme defines values for: default, **hover, active, focus, disabled**,
borders, raised surfaces and shadows. Background + text alone is not
enough — missing states are the most common source of visual bugs. Both themes
need a **visual QA pass** before merging, not just a code review.
