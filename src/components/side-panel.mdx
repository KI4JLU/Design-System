# SidePanel

> **Internal part of `AppShellLayout`.** Apps get their side columns from
> `AppShellLayout` (Templates), which composes `SidePanel` and `ResizeHandle`;
> use it directly only to build a new shell template.

The frame of a collapsible workspace panel: width, collapsed state, edge side.
Replaces the hand-built duplication of "left panel" and "right panel" — the
position is a prop, not a separate part of the component.

## Props

| Prop | Type | Required | Meaning |
|---|---|---|---|
| `side` | `'left' \| 'right'` | ✅ | Edge side: decides the border **edge** (`border-r` on the left, `border-l` on the right) and the chevron direction — see "Chevrons" below. |
| `isOpen` | `boolean` | ✅ | Expanded, or collapsed to the rail. **Consumer state.** |
| `width` | `number` | ✅ | Width in px when expanded. **Consumer state.** |
| `onExpand` / `onCollapse` | `() => void` | ✅ | Click on the expand or collapse button. |
| `expandLabel` / `collapseLabel` | `string` | ✅ | Accessible names of the two buttons. |
| `header` | `ReactNode` | — | Title/brand node in the header row, **only when expanded** — see "Header row" below. |
| `collapsedPreview` | `ReactNode` | — | Icon strip in the collapsed rail, below the expand button. |
| `footer` | `ReactNode` | — | Node pinned below the body (e.g. `SidebarUserMenu`), **since 0.30.0**; survives collapsing and moves to the bottom end of the rail. |
| `children` | `ReactNode` | ✅ | Content of the panel. |
| `aria-label` | `string` | (recommended) | `<aside>` is a `complementary` landmark; with more than one panel on the page, each needs its own name. |

## Header row

The row with the collapse button also carries the optional `header` node, and
the button sits **on the edge facing the content** — in both directions:

| `side` | Order of the header row |
|---|---|
| `left` | `[header … button]` — button at the trailing edge |
| `right` | `[button … header]` — button at the leading edge |

Two panels of one view thus mirror toward the middle: both controls sit at the
main area, not at the window edges. This is carried by the **DOM order** (not
by an `order-*` utility), so that tab order and reading order match the
picture.

The row is `h-14` tall — the same chrome unit as the `AppShellLayout` bar, so
that the left header row, the main column's bar and the right header row line
up. The height belongs to the row, not to the button, so a taller `header`
node doesn't shift anything.

### Geometry: the toggle sits on the body's first control

Since 0.39.0 the row is inset with **`px-4` (16px)** and the toggle is
**32px** wide (`p-1.5` instead of the `icon` variant's 8px, plus the 20px
icon). Its center is therefore 16 + 16 = **32px** from the panel edge —
exactly where a 32px control sits at the trailing edge of the first row of a
`p-4`-padded body (16px padding + 16px half width). Header row and body thus
stand on one vertical line instead of missing each other by 10px: up to
0.38.0 the row was `px-gutter` (24px) and the button 36px wide, so its center
was at 42px.

Both buttons are the same control in two positions and therefore the same
size — the expand button in the 60px rail has the same 32px, otherwise it
would jump on collapsing. The inset is deliberately **no longer** that of the
`AppShellLayout` bar (which stays at `px-gutter`, 24px, for its own content).
Measured in Chromium by `SidePanel` → `ToggleAlignsWithBodyControl`, whose
expectation comes from the rectangle of the body control itself, not from a
typed number.

`header` sits in a `min-w-0` wrapper: a title with `truncate` is shortened
with an ellipsis instead of pushing the button out of the row. Whether it is
truncated, wrapped or not shrunk at all is decided by the consumer's node.

Since 0.30.0 there is a `footer` slot: it is pinned below the scrolling body
and **moves into the rail when collapsed**, because it is typically the only
way to sign out. (Up to 0.29.0 this page said a composing shell should pin its
footer itself in `children` — that is no longer true.)

## Chevrons

Each of the two buttons has its **own** icon, because a chevron has to point
in the direction it moves the panel: collapsing pushes the panel to its own
edge, expanding pulls it back toward the content.

| `side` | collapse | expand |
|---|---|---|
| `left` | `PanelLeftClose` (points left) | `PanelLeftOpen` (points right) |
| `right` | `PanelRightClose` (points right) | `PanelRightOpen` (points left) |

What counts is lucide's path data, not the name: `panel-left-close` has the
chevron `m16 15-3-3 3-3` (tip on the left), `panel-left-open` `m14 9 3 3-3 3`
(tip on the right). Both states are tested — a test that only renders the
expanded state never sees the expand button.

## Decisions

- **Controlled only.** `isOpen` and `width` live with the consumer — an app
  typically keeps both in a context, persists them and has to share them with
  a `ResizeHandle` and the template. State of its own in the frame would be a
  second source of truth.
- **The collapse button belongs to the frame, not to `children`.** In the
  collapsed state it is the only control — passed as content, it would be
  gone exactly when it is needed.
- **Rail width: a constant, not a prop.** `SIDE_PANEL_RAIL_WIDTH` = 60px is a
  design constant — the rail carries exactly one icon button and a narrow
  preview strip; a freely chosen value could only make it too small for the
  touch target, or so wide that it looks like a broken panel. The **expanded**
  width, on the other hand, is state (the user drags it) and therefore a prop.
  The constant is exported so a template uses the same value instead of
  repeating it.
- **`header` is unmounted when collapsed — `children` is not.** Exactly the
  opposite, and on purpose: a panel body holds the scroll position and
  half-typed input; a header row is chrome without state, and of the chrome
  only the expand button stays in the rail — next to `collapsedPreview` and
  the pinned `footer`. Anything stateful therefore belongs in `children`, not
  in `header`.
- **Content stays mounted.** When collapsed, the body carries the `hidden`
  attribute (and `display:none`): scroll position and half-typed input survive
  collapsing, and at the same time the content is removed from the
  accessibility tree.
- **No width transition.** The same width is also dragged with the mouse; an
  animated width would trail behind the pointer.
- **The rail mirrors the expanded column vertically** (0.35.0). It doesn't
  build its own rhythm but the same three boxes: the `h-14` chrome row for the
  expand button, below it the scrolling preview area with the padding a column
  body brings, below that the unpadded `footer`. That way every control keeps
  its height on the page when collapsing. Before, the button sat in the same
  padded box as the preview: the icon strip sat 12px too high, the button 2px
  off the header row's center, and the footer 16px too high (measured in
  Chromium — the story `AppShellLayout` → `CollapsedRailKeepsVerticalPositions`
  run against the old rail: 68 instead of 80, 34 instead of 32, 32 instead of
  16, each relative to the column's box).
- **`collapsedPreview` is not button content.** The expand button is a
  separate small control above the preview — not the whole rail. A
  rail-as-button would nest interactive elements in the preview (invalid HTML)
  and pull their text into the accessible name. The price: a click anywhere on
  the rail does **not** expand it.

## Do's & don'ts

- ✅ Set the edge side via `side` — the panel draws exactly one line, the
  `ResizeHandle` none.
- ✅ Pass all labels as props (bilingual consumers).
- ✅ Pass the title in the `header` slot with `truncate`, not as the first row
  in `children` — otherwise it scrolls away and doesn't sit on the chrome
  line.
- ❌ No collapse button of your own in `children`.
- ❌ No stateful UI in `header` (it is unmounted on collapsing).
- ❌ Don't expect viewport logic here: whether a panel appears at all on narrow
  screens (usual: one view plus `BottomTabBar`) is decided by the composing
  template (`AppShell`).
