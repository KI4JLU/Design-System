# Container

The centered page column: page margins from the spacing tokens (`px-gutter`
on mobile, `px-margin-page` from `md` up) and **one named page width**. Every
page sits in a `Container` — directly, or through a template
(`TableLayout`, `DashboardLayout`, `SectionedGridLayout`, `AppShellLayout`)
that renders one itself.

## Which width do I use?

`size` names the **role of the page**, not a size step. That is the whole
decision, and it has exactly three answers:

| `size` | Token | Width | Measure* | Chars/line* | For |
|---|---|---|---|---|---|
| `page` (default) | `--max-width-container-max` | 1440px | 1360px | ~181 | The content uses the whole area: dashboards, wide tables, editor views, app chrome. |
| `content` | `--max-width-container-content` | 1000px | 920px | ~121 | **The normal case for a page**: cards, grids, sections, overviews, detail pages. |
| `reading` | `--max-width-container-reading` | 672px | 592px | ~74 | One column of running text or form fields. |

\* Measure = width minus page margins (`box-sizing: border-box`, so 2 × 40px
from `md` up). Characters per line measured in Chromium, Inter 16px, German
legal text; the number varies by a few percent with the text.

**The rule of thumb: `content` when the page shows content; `page` when the
content needs the area; `reading` when it is text or a form.** `page` is the
default because it was the value before there was a choice — not because it
is the most common answer. A new page usually starts at `content`.

### Running text doesn't belong in `content`

`content` is a **page** width, not a reading measure: at a 920px measure,
~121 characters run into one line, and WCAG 1.4.8 (AAA) limits that to 80.
For pages made of cards, grids and tables that doesn't matter — they carry no
long paragraphs. But as soon as a page shows **one paragraph after another**
(terms of use, privacy policy, accessibility statement, a help page),
`reading` is the right width: ~74 characters, so below the limit. A page that
mixes both uses `content` and limits its text block inside — not the whole
container.

## Why `content` is 1000px

Measured, not chosen. The content columns JustRAG used when the size was
added:

| Where | Width |
|---|---|
| JustRAG `.home-view__section` / `.home-view__grid--main` (KB overview) | **1000px** |
| JustRAG `GlobalKbSettings` (inline) | 900px |
| JustRAG `Profile` (inline) | 800px |
| JustRAG `.admin-container` (admin tabs) | `min(1600px, 95vw)` |

So between `reading` (672px) and `page` (1440px) there are 800, 900 and twice 1000 — and 1000 is
the width the next page to move over should align with (KI-750: JustRAG's
legal pages should match the KB overview). The Tailwind step `max-w-5xl`
(1024px) would have been the more convenient number, but would have missed
that alignment by 12px per side — and thus brought back exactly the
`max-w-[1000px]` at the call site that this width is meant to get rid of.
`px` and not `rem`, because `page` and `content` limit device space (cards,
grids, tables); `reading` is a text measure and is therefore in `rem`, so it
grows with the user's font size.

## Why `size` and not `className="max-w-[…]"`

Because nobody notices the class at the call site. `layout-only-classname`
only checks the `DS_CONTROLS` list in `eslint-plugin/index.js` (Button, Input,
Textarea, Badge, MenuItem, NavItem, Switch, SegmentedControl, CodeBlock) —
**composition components like `Container` are not in it**, so the rule
structurally can't see a `max-w-[1000px]` here (KI-711). A width at the call
site is thus invisible to lint, to Storybook and to anyone who wants to read
the system's width scale — and the scale becomes a recommendation instead of
a rule.

Technically the class *works*: the width utility sits on exactly the element
`className` flows into, `cn()`/tailwind-merge resolves the conflict, and the
class wins. This story pins the mechanism down so it doesn't flip unnoticed —
it is not a recommendation:

If a width is missing, it comes **here** (a token in `tokens.css`, an entry
in `container-variants.ts`, a row in this table) — not into a class at the
call site.

## Why the tokens are referenced as `max-w-(--token)`

All three widths are written as `max-w-(--max-width-container-*)` in
`container-variants.ts`, even though Tailwind 4 also generates the utilities
`max-w-container-max` / `-content` / `-reading` from the same tokens
(measured with tailwindcss 4.3.2 against this package — the earlier note in
the variants file saying there was no `--max-width-*` namespace was wrong).
The reason is **tailwind-merge**, which `cn()` runs on every `Container`:
measured with tailwind-merge 3.6.0,

```
max-w-(--max-width-container-content) max-w-3xl   →   max-w-3xl
max-w-container-content max-w-3xl                 →   max-w-container-content max-w-3xl
```

A custom theme key is not in tailwind-merge's `max-w` conflict group, so both
classes stay and the CSS order decides — the width at the call site then no
longer wins reliably. The `max-w-(--token)` form is therefore the pattern
here; a bare Tailwind step (what `reading` used to be) is the second working
form, but hides the value from `tokens.css` and can't be adjusted in one
place.

## Renaming (0.25.0)

The sizes used to be called `default` and `narrow` — describing position, and
so with no answer to the question "which one do I use?". New:

| before | now | width |
|---|---|---|
| `default` (default) | `page` (default) | 1440px, unchanged |
| `narrow` | `reading` | 672px, unchanged |
| — | `content` | 1000px, new |

**No width has moved** — only the names. If you never set `size`, you are not
affected; `size="narrow"` becomes `size="reading"` and `size="default"`
becomes `size="page"` (both break as type errors, not silently).

## Do's & don'ts

- ✅ New page: start with `size="content"` and only switch to `page` when the
  content really needs the area (wide table, dashboard).
- ✅ Legal texts, help pages, forms: `size="reading"`.
- ✅ Use `asChild` when the column should be a `<main>`/`<section>`, instead
  of nesting an extra `div`.
- ✅ Vertical spacing at the call site (`py-gutter md:py-margin-page`) — it
  belongs to the page, not to the width.
- ❌ No `className="max-w-[…]"` and no `max-w-*` at the call site to set a
  page width. Lint doesn't see it (see above) — if the width is missing, it
  goes into the system.
- ❌ No second `Container` in a template that already renders one: the page
  margins then add up.
- ❌ No long stretches of text in `page` or `content` — the measure clearly
  breaks the 80-character limit of WCAG 1.4.8.
