# ResizeHandle

> **Internal part of `AppShellLayout`.** A resizable column gets its handle
> from `AppShellLayout` (`leftResize`); use `ResizeHandle` directly only
> between two areas the shell does not own.

The accessible drag handle between two areas. Replaces inline-styled `div`
handles with their own keyboard logic at each call site.

## Props

| Prop | Type | Required | Meaning |
|---|---|---|---|
| `side` | `'left' \| 'right'` | ✅ | Side of the panel being resized — flips the arrow direction. |
| `value` | `number` | ✅ | Current width in px (`aria-valuenow`). |
| `min` / `max` | `number` | ✅ | Limits (`aria-valuemin` / `aria-valuemax`, Home / End). |
| `step` | `number` | — | Step size of the arrow keys, default `10`. |
| `label` | `string` | ✅ | Accessible name (`aria-label`). |
| `controls` | `string` | — | `id` of the panel this handle resizes (`aria-controls`). Needed for full APG conformance; optional so a handle can still be used without a known `id`. |
| `onValueChange` | `(value: number) => void` | ✅ | Receives **every** clamped width — keyboard and mouse alike. |
| `onResizeStart` / `onResizeEnd` | `() => void` | — | Notification that dragging starts/ends. |

## Ownership: the handle owns the interaction, the consumer owns the value

**Decided, not to be split.** On `pointerdown` the handle itself attaches the
`pointermove`/`pointerup` listeners to `window`, computes the new width from
the distance moved, clamps it to `[min, max]` and reports it through
`onValueChange`. The consumer stores **one** number.

- The transient "being dragged" state stays internal — it is interaction
  state like `:hover`, not data. That is why there is no `active` prop: the
  handle knows it itself and colors itself `bg-primary`.
- `onResizeStart` / `onResizeEnd` are **notifications** (for example, to
  suspend an expensive recalculation while dragging), not a mechanism. An
  extra `pointermove` loop in the consumer is exactly the half-shared state
  this component does away with.
- On unmount in the middle of a drag, the listeners are removed.

## Role & ARIA

The handle is a **focusable `separator`** — the WAI-ARIA APG pattern "Window
Splitter", the pattern for exactly this widget. Concretely:

- `role="separator"` with `tabIndex={0}` (in the tab order, because it is
  operable), plus `aria-valuemin` / `aria-valuemax` / `aria-valuenow` and
  `aria-label`.
- `aria-orientation="vertical"` describes the orientation **of the dividing
  line itself**. For `separator`, `horizontal` is the default, so "vertical"
  has to be stated explicitly — a vertical bar between two areas side by
  side.
- The keys are **directional**: they move the dividing line, and
  `aria-valuenow` reports the width of the *area*. That is why the same key
  widens a left panel and narrows a right one.
- **`aria-controls`** points, via the `controls` prop, at the area whose size
  is reported — the "primary pane" in the pattern. The reference must point at
  an **existing** element: a dangling `aria-controls` is worse than none, so
  without `controls` the handle renders no `aria-controls` at all (and one
  smuggled in via spread is dropped — the prop is the one way in).

**With that, the pattern is fully implemented.** Measured against the WAI-ARIA
APG page "Window Splitter": all required properties — focusable
`role="separator"` (`tabindex`), `aria-valuenow` / `aria-valuemin` /
`aria-valuemax`, an accessible name, `aria-controls` on the primary pane, an
explicit `aria-orientation` — and the required arrow keys (`←`/`→` for a
vertical dividing line). Of the keys the pattern lists as **optional**,
`Home`/`End` are implemented; not implemented are:

- **`Enter`** (collapse / restore the area). Collapsing and expanding belongs
  to the `SidePanel` — there it is a visible button, not a hidden shortcut on
  the handle.
- **`F6`** (cycle through the areas) — that is app-chrome navigation, not a
  property of a single handle.

Both are omissions of *optional* parts, not deviations from conformance.

## Decided: `aria-controls` points at the panel root

Two questions were open (card KI-597): *which* element the handle references
and *who* mints the `id`. Both are decided:

**1. The target is the root of the panel** — in the shell, the `SidePanel`'s
`<aside>`, i.e. the named `complementary` landmark — and **not** the inner
content area that the `SidePanel`'s collapse/expand buttons point at with
their own `aria-controls`. The two references mean different things and stay
separate: the button controls the **visibility** of the content (paired with
`aria-expanded`; the target is the element that gets `hidden`), the handle
controls the **size** of the panel — and the root carries the width
(`style.width`), not the content area. On top of that, a screen reader that
follows the reference lands on a **named** landmark instead of an anonymous
`div`.

**2. `AppShell` mints the `id`** (with `useId`), not the `SidePanel`. The
template is the one place that composes panel and handle — so the one place
that knows both ends of the reference. `SidePanel` needs no API change for
this: the `id` travels through the root attribute that is passed through
anyway, and the content area's internal `id` stays the `SidePanel`'s
business. A standalone handle gets the `id` directly through `controls`.

## Keyboard

| Key | Effect |
|---|---|
| `→` / `↑` | left panel **wider**, right panel **narrower** |
| `←` / `↓` | left panel **narrower**, right panel **wider** |
| `Home` | `min` |
| `End` | `max` |

The pattern assigns `←`/`→` to a vertical splitter — the axis this bar
actually moves along. `↑`/`↓` are additional **aliases** of `→`/`←` and mirror
per side in the same way: one widget, one behavior, whichever axis the user
reaches for. On a vertical splitter the vertical keys have no other meaning in
the pattern, so the alias is an extension, not a contradiction.

The arrows follow the **direction** and therefore mirror with `side`: the
edge of a left panel is on its right, the edge of a right panel on its left.
`Home`/`End`, on the other hand, are **values** (the announced minimum and
maximum), not directions — they don't mirror. Both directions are pinned per
side with a test; swapping them is the obvious mistake.

`aria-valuenow` is always within `[min, max]` — both input paths clamp, and a
stale value from the consumer is announced clamped as well.

## Appearance

**Since 0.38.0 the handle takes up no layout width.** The host is `w-0`, the
hit area an `::after` overlay: `absolute inset-y-0 -left-1 w-2`, i.e. 8px
**over** the border line, 4px into each neighbor, laid over both with
`relative z-10`. It stays borderless and invisible at rest as before; `hover`
tints the overlay with `bg-outline-variant`, `bg-primary` fills it while
dragging, and the focus ring sits on the overlay too — the host has no box a
ring could sit on. The border line between the area and the content is still
drawn by the `SidePanel` (`side`), not by the handle — so there are no two
neighboring 1px lines and no negative margins are needed.

That is the usual splitter shape: **zero width in the row, a wide hit area on
top.** The reason is a report from JustRAG's knowledge base view (09/2026): as
a 6px wide transparent flex item the handle pushed its neighbors apart, and
the shell's `bg-surface` background showed through the gap — a visible tinted
stripe between two `bg-surface-container-lowest` surfaces. A single track
color can't match both neighbors at every height; zero width needs none at
all.

The hit area is therefore 8px wide instead of 6px: deliberately a pointer and
keyboard affordance for wide viewports. On narrow screens no widths are
dragged — there the `BottomTabBar` switches the view — so no 44px touch target
is provided here.

Geometry and hit testing are pinned in Chromium, not in jsdom:
`AppShellLayout` → `HandleHasNoLayoutWidth` measures that the box is 0px wide,
that the left column's right edge **is** the main column's left edge, that
`elementFromPoint` on that line returns the handle at ±3px (and no longer at
±5px), and that a drag started at a point found that way still resizes.

Screen readers announce `aria-valuenow` as a bare number. If you want users
to hear "320 Pixel", also pass a translated `aria-valuetext` — the prop is
passed through.

## Decided: `separator` instead of `slider`

There was an open double question here — the role, and the mirroring of the
vertical keys. Both are decided (design system owner, 08/2026); the section
stays as a record so the question isn't reopened.

**1. The role is `separator`, not `slider`.** `slider` was taken over from the
app that pioneered this pattern; the APG pattern for exactly this widget is
"Window Splitter" with `role="separator"` and `tabindex`. The repo prefers
standards over home-grown solutions, and the switch also fixes the actual
defect: under `slider`, `aria-orientation` means the axis along which the
**value** moves (horizontal here) — so "vertical" was wrong there. Under
`separator` the same attribute describes the orientation of the **dividing
line**, and that is vertical. `aria-orientation="vertical"` therefore stays
and is now correct instead of contradictory (details under "Role & ARIA").

**2. The mirroring of the vertical keys stays exactly as it is.** Because `↑`
is an alias of `→` and `→` makes a **right** panel narrower, `↑` decreases
`aria-valuenow` there. Under `slider` that contradicted the common expectation
that `↑` increases the value — under `separator` the keys are directional
(they move the dividing line), so the mirroring is the pattern, not a
deviation from it. The role decision answers both questions at once: **nothing**
changes in the keyboard behavior.

A purely accessibility-side change: no markup changes except the ARIA
attributes, no class and no token — **zero visual effect**.
