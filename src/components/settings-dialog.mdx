# SettingsDialog

An app's settings window: on the left a column with search and one row per
section, on the right the selected section under its title, and the close
button at the top right as in every `Dialog`. Radix Dialog underneath — focus
trap, Escape and scroll lock included.

The content belongs to the app: every section is a list of `SettingsRow`s
(label + description on the left, control on the right, a line below). For
appearance the package ships the ready-made rows — **`AppearanceSettings`**.

<Canvas of={SettingsDialogStories.Default} />

## Groups

When the window has many sections, a flat list doesn't say which belong
together (an app's admin window has a dozen). `group` on a section puts a
small gray heading above every block of consecutive sections with the same
value — in the font of the sidebar's list title, as a `role="group"`, named
after the heading.

<Canvas of={SettingsDialogStories.Groups} />

```tsx
sections={[
  { value: "models", label: "KI-Modelle", group: "Konfiguration", content: … },
  { value: "auth", label: "Anmeldung", group: "Konfiguration", content: … },
  { value: "overview", label: "KB-Übersicht", group: "Wissensbasen", content: … },
]}
```

- **Title.** As soon as a section has a `group`, the column no longer shows a
  title of its own: the gray list label is dropped so it doesn't sit above the
  first group heading. `title` stays the window's name for screen readers.
  Without groups everything stays as before.
- **Keep them together.** The heading stands before every block; if a group's
  sections aren't next to each other, it appears more than once.
- **Without `group`** a section stands loose, without a heading — windows that
  don't use `group` look as before.
- **Search:** a group without matches loses its heading too.

## Search in the settings

The search at the top left finds not only sections (by `label` and
`keywords`), but also the individual `SettingsRow`s in the open section: the
label and description of every row are searched.

- **Matches** are highlighted everywhere in the section — in lists, tables and
  headings too (CSS Custom Highlight API; the text itself stays unchanged).
  Only rows are filtered.
- **Everything else is hidden:** rows without a match, but also headings,
  introductions and cards that contain no matching row. The rules are in
  `tokens.css`.
- **If the search names the section itself** ("Agenten"), it stays fully
  visible; it is only highlighted.
- **No match in the rows:** the section stays whole instead of appearing
  empty. The open section stays in the list as long as its rows match, even if
  its name and `keywords` don't — the search still finds other sections only
  by name and `keywords`, because only the open section is rendered.

Every rendered `SettingsRow` in the window takes part. Two helpers for the
content:

- **`useSettingsSearch()`** returns `{ query, filtering }`. The search doesn't
  find rows in parts that aren't rendered (collapsed `Collapsible`s) — the
  content opens such parts while `filtering` holds; the window hides parts
  without matches.
- **`data-search-keep`** on a group heading keeps it visible as long as its
  container is visible. `PanelSection` sets it on its title row.

## Maximize

`maximizable` puts a toggle to the left of the close button ("Maximieren" /
"Wiederherstellen"): when maximized the window fills the screen — 1rem inset
from `sm` up, edge to edge below that — whatever `size` and `fitTo` say.
Meant for editors with long forms or wide tables. Without `maximized` the
window remembers the state itself (it starts normal); with `maximized` +
`onMaximizedChange` the app holds it, for example to keep it across sessions.

```tsx
<SettingsDialog size="xl" fitTo={area} maximizable … />
```

## `AppearanceSettings` — the "Darstellung" section

Three `SettingsRow`s, each with a DS `Select`, each bound directly to the
provider that owns the setting:

| Row | Values | Hook | Effect |
|---|---|---|---|
| Farbschema (color scheme) | System / Hell / Dunkel | `useTheme` (`ThemeProvider`) | `<html data-theme>` |
| Kontrast (contrast) | System / Standard / Mittel / Hoch | `useContrast` (`AppearanceProvider`) | `<html data-contrast>` |
| Akzentfarbe (accent color) | the six `ACCENT_COLORS`, each with an `AccentSwatch` | `useAccent` (`AppearanceProvider`) | `<html data-accent>` |

The component holds **no state of its own**: a choice calls the provider's
setter, the provider stores it (`localStorage`) and mirrors it onto
`<html>` — just as for every other caller. What the rows show is therefore
always what currently applies, even if it was changed elsewhere (for example
from the Storybook toolbar).

```tsx
import { AppearanceSettings, SettingsDialog } from "@ki4jlu/design-system";

<SettingsDialog
  open={open}
  onOpenChange={setOpen}
  sections={[
    {
      value: "appearance",
      label: "Darstellung",
      icon: <Palette aria-hidden="true" />,
      // The row labels, so the search finds the section.
      keywords: ["Farbschema", "Kontrast", "Akzentfarbe", "Stil"],
      content: <AppearanceSettings />,
    },
    // … the app's own sections (profile, API keys, …)
  ]}
/>
```

- **Prerequisite:** a `ThemeProvider` above it (`useTheme` throws without
  one) and an `AppearanceProvider`. Without the `AppearanceProvider`,
  contrast, accent and style show their defaults and a choice does nothing —
  the hooks' documented read-only behavior.
- **A fragment, not a wrapper.** The rows are rendered without an enclosing
  element. That way they can be mixed with the app's own rows in the same
  section (for example a language choice below), and the lines between the
  rows stay continuous.
- **Labels:** every text can be overridden through `labels`
  (`AppearanceSettingsLabels`, German defaults). Keys that are not set, or set
  to `undefined`, keep the default; `null` or `""` on a `*Description` removes
  the description. `accents` overrides only the names it contains.

```tsx
<AppearanceSettings
  labels={{
    theme: "Colour scheme", themeLight: "Light", themeDark: "Dark", themeSystem: "System",
    contrast: "Contrast", contrastNormal: "Standard", contrastMedium: "Medium", contrastMore: "High",
    accent: "Accent colour", accents: { standard: "Default", teal: "Teal" },
  }}
/>
```

- **Accessibility:** every `Select` is named after its row label via
  `aria-labelledby` and linked to the row description via `aria-describedby`,
  if there is one.

### Deliberately not included

Language, profile fields, API keys and app-specific switches (suggestions,
follow-up questions, …) stay in the app. They depend on app state and i18n
the package doesn't know; the app adds them as its own `SettingsRow`s next to
`<AppearanceSettings />` or in sections of its own.

## Opening from the user menu

The usual way into the window is "Einstellungen" in the `SidebarUserMenu`: the
menu item sets the `open` state via `onSelect`, which the `SettingsDialog`
receives as a controlled prop.

<Canvas of={SidebarUserMenuStories.OpensSettings} />

```tsx
const [settingsOpen, setSettingsOpen] = useState(false);

<SidebarUserMenu initials="JL" name="Jamie Lee" role="Admin">
  <DropdownMenuItem onSelect={() => setSettingsOpen(true)}>
    <Settings width="1em" height="1em" aria-hidden />
    Einstellungen
  </DropdownMenuItem>
</SidebarUserMenu>
<SettingsDialog open={settingsOpen} onOpenChange={setSettingsOpen} sections={sections} />
```

The story checks in the browser (Chromium) that the menu closes behind the
dialog and that the page is usable again after closing (no leftover
`pointer-events: none` on `<body>`).

### Known gap: focus after closing

After closing, focus lands on `<body>`, not back on the element that opened
the window (WCAG 2.4.3). The cause: Radix's modal dialog always moves focus
to its own `DialogTrigger` on close — `SettingsDialog` renders none, because
it is opened as a controlled component. That applies to every way of opening
it, a plain button included; delaying `setOpen` (`setTimeout`,
`requestAnimationFrame`) changes nothing (measured). Not fixed yet — reported
as a follow-up card.
